# citations — inline citations and a bibliography

A plugin, not an asset. Type `@@` in the document, pick a reference, and the citation
appears as one unbreakable mark; the bibliography at the foot of the page renumbers itself.
`lab/017-inline-marks/` is where it was built and measured.

```
Insert ▸ Citation…    the same picker the `@@` trigger opens, at the caret
References            the library: import a .bib or CSL-JSON (file picker or paste), fetch a
                      Zotero library, choose the style, turn the reference list
                      off / cited only / whole library, resolve changed references
```

Both `@@` and **Insert ▸ Citation…** open the same picker. The menu path needs a caret anchor,
because opening a menu moves focus out of the document and `content.focus()` then puts the
caret on the element rather than in the text — so the plugin remembers the last caret and
falls back to the end of the last text block. Escape and a click outside both close it.

## Reading a Zotero library

A Zotero library is not a bibliography. It holds the PDFs (`attachment`), the notes taken while
reading (`note`), and Zotero 7's `annotation` items — one per highlight and comment in every
PDF, each carrying `annotationText` and a `parentItem` pointing at the attachment it sits in.
Zotero serialises an attachment as **CSL type `document`**, the same type a real document item
uses, so the CSL-JSON side cannot tell them apart. Importing the CSL list unfiltered therefore
adds hundreds of highlights as if they were books — measured on a real library: **848 items, of
which 334 are references.**

The reader filters in two places:

- **server-side**, `itemType=-attachment` — the API accepts exactly one negated type
  (`itemType=-attachment||note` is `400 Invalid itemType`, measured), and attachments are the
  bulk of a library's items;
- **client-side**, `isReferenceItem()` on the item JSON this client already fetches for Better
  BibTeX keys: a reference is **top level** (no `parentItem`), **not deleted**, and **not** an
  attachment, note or annotation.

The **item JSON decides what is a reference**, and the CSL-JSON only supplies the fields,
matched on the item key. Doing it the other way round is the bug.

Paging is by `total-results` (a short page is the end; 20 pages is the bound), and the panel
reports what it took and what it left: *571 references imported of 848 items · skipped 277
notes*.

## Importing twice

A `.bib` is regenerated by a tool that may have corrected a year; a Zotero item may have
been edited since the citation was made. So a re-import does **not** overwrite a reference the
document already cites. It classifies every key — new, already current, or changed — and a
changed one is a row with both copies side by side and two buttons, `Update` and `Keep mine`.
Nothing is merged and nothing is guessed, the same shape as `File › Import comments…`.

A key that changed is not an update: `smith2020a` and `smith2021a` are two references, and the
document keeps the one it cites.

## Publishing

    node tools/publish-plugin.mjs          # dist/cdn/plugins/citations/citations.js
                                           # dist/plugins/citations.json
    node build.mjs combine                 # the catalog row, in dist/registry.json

`tools/publish-plugin.mjs` holds a descriptor per bundle; `publishedBundles()` derives the
catalog's `bundles` entry from the manifest bytes it just wrote, so the advertised hash and the
manifest cannot drift. `check` fails when either is stale, and `bundleProblems()` refuses a pin
that jsDelivr would not serve.

One file, because that is a requirement rather than a preference: the loader evaluates verified
bytes from a `blob:`, where nothing bare or relative resolves. So the parsers, the picker and
the bibliography are one module, and the pure parts are *exported* so `lab/017`'s tests import
**this file** — the tested bytes are the shipped bytes (`test/browser/citations.spec.js` covers
the same ground in CI).

## What it asks the host for

Two generic capabilities, both added for this and useful to anything else:

| capability | what it does | why a plugin cannot do it |
|---|---|---|
| `editor.insertInline(node, {removeBefore})` | inserts an inline atomic at the caret, spends the typed trigger, **records one history entry** and marks the document dirty | the three duties of a content change are the editor's; a plugin that remembers two of them is a bug |
| `pagination.defineBlock(tag, spec)` | teaches the planner that `<section>` is lines, not whole | a reference list longer than a page has to fragment |

And one host API bump it needs: **`api: 2`**, because `insertInline`, `defineBlock`, `data-atomic`
and the `data-plugin-style` rule all arrived together. A host that does not have them refuses
the plugin *before* `activate()` instead of failing halfway through a citation.

And one core rule it relies on, which is not a capability because it is not code a plugin
calls: **`data-atomic` on an inline element means the planner may not cut inside it.** Without
it a page break that lands inside `[7]` clones the element — two marks, one `data-keys`, and
in Safari sometimes an empty clone. Measured in `lab/017` across three engines; 0/240 splits
for `[7]` in Latin prose (the word-boundary back-off protects it by accident) and 7/240 for
`(Author7 2007)` in CJK, where nothing backs up.

## What it writes into the document

Because it is a plugin, everything it needs at read time has to be *in the file*:

| block | why it is content |
|---|---|
| `<a class="cite" data-keys data-atomic>` | the label is derived but **saved**: `[3]` is ordinary text with no plugin running |
| `<section id="bibliography" data-generated>` | a saved block, not a render: a reader without the plugin still reads the reference list |
| `<style id="citation-styles" data-plugin-style="citations">` | a plugin may contribute document-level CSS that survives a save; this is the first one that does |
| `<script id="citation-store" type="application/json">` | cited entries only, CSL-JSON: the repair path for the next activation |

The picker is `data-plugin-ui` + `data-runtime="ephemeral"`, so `session.strip()` drops it and
it never reaches a file.

## What does not degrade

Renumbering. Without the plugin the numbers are a snapshot of the last save — a reader sees a
correct document, but only an editor running the plugin can renumber it. That is the honest
boundary of "a plugin, not an asset", and it is why the store travels: enabling the plugin on
a document somebody edited in between re-derives every label from `data-keys`.

## Styling

Two stylesheets, on purpose:

- `STYLE_TEXT` → `<style data-plugin-style="citations">` in `<head>`, **saved with the file**,
  because a reader without the plugin needs the rule that makes a citation legible;
- `PANEL_CSS` → `<style data-plugin-ui id="citation-ui">`, **session chrome**, removed with the
  dialog. The panel uses `cp-*` classes: `.ds-*` belongs to the document settings dialog and is
  scoped to `#doc-settings-dialog`, so borrowing those names rendered an unstyled box.

## Known limits

- **Undo/redo relabel via `host.on("restore")`** (host api 2). One undo removes the whole
  insertion; a redo re-derives the label, because the restored snapshot predates the relabel.
- **Locators** (`[1, p. 33]`) are not modelled.
- **CSL is not implemented.** Three hand-rolled styles. The store is CSL-JSON so a processor
  (citeproc-js, citeproc-rs, or pandoc's own, which the export path already carries) can be
  dropped in behind `label()`/`formatEntry()`.
- **`defineBlock("section", …)` is keyed by tag**, so it is only applied when the document has
  no other `<section>`; otherwise a long bibliography stays atomic.
- **No CSL files are pinned.** The three styles are hand-rolled; `styles.mjs` proves the real
  ones are pinnable, and the store is already CSL-JSON.
